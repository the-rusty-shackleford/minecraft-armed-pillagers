# D-0002 — Profiles and loadouts ship in this jar, guarded; the bridge is code only

**Decision**: The `rangedweapons:weapons` profiles and the
`armedpillagers:pillager_loadouts` entries for Another Gun Mod's guns ship in
this mod's own resources, every entry carrying a
`neoforge:mod_loaded` condition on `anothergunmod`. The bridge ships no data.

**Why**: Two facts read from the NeoForge source settled it. A data-map file
for a type nobody registered is not ignored: `DataMapLoader` warns on every
reload, so a bridge shipping `armedpillagers:pillager_loadouts` would nag any
server running the bridge without this mod — and the bridge must not depend
on this mod (D-0001). And the profiles must be present *without* the bridge
for the fallback path to work at all: a pack with the gun mod and this mod but
no bridge still gets shooting pillagers, on the protocol's tracer, from the
same guns. With the conditions, the one jar does the right thing in every
combination — native fire with the bridge, fallback fire without it, nothing
and no warning without the gun mod.

The plan had the data moving to the bridge; this reverses that, on evidence.

**Alternatives rejected**: *Data in the bridge* — the reload warning above,
and no fallback path without the bridge. *Data in both* — the same entry
twice, with the later pack winning silently; a maintenance trap. *Unguarded
entries* — an entry naming an absent mod's item is a hard datapack load error
(`DataMapLoader.buildDataMap` skips a condition-failed entry before resolving
it; an unguarded one is resolved as required).

**Follow-ups**: A profile for a gun this jar does not know is a pack author's
one-file job; the README shows the shape.
